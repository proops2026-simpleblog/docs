# DOP-001 — Blog / CMS Platform

**PIC (Product Owner / Overall):** Dat Pham & Trung (co-owned)
**Status:** ACTIVE · **Last audited:** 2026-10-17 (Day 21)

**Problem statement**
Small teams writing blog posts struggle with having no central place to draft and categorize their content, causing drafts to be scattered and making it impossible for readers to filter published work by category.

**Solution**
Our Blog / CMS Platform solves this by providing a single shared workspace where Authors can draft, categorize (one category per post), and publish content through a clear status lifecycle (DRAFT → PUBLISHED → ARCHIVED), while allowing Readers to browse filtered posts and leave comments.

**Scope decisions**
- Single shared workspace application (not a multi-tenant SaaS) — all Authors and posts live in one shared space, no per-team data isolation.
- One category per post (`categoryId` is singular and nullable).
- Explicit 3-state post lifecycle: `DRAFT → PUBLISHED → ARCHIVED`.

**Out of scope** *(added Day 21)*
- Multi-tenancy / per-team data isolation.
- Caching layer / Redis — installed with Helm during training (Day 16), used by no service; **removed by decision 2026-10-17** (Trung + Dat). Not part of this product until a DOP AC requires it.
- Production frontend build (Nginx static bundle) — frontend runs the Vite dev server (IRD-004).
- Email verification, password reset, OAuth/SSO.
- Media uploads on posts; full-text search beyond the category filter.
- Admin UI — Admin actions are exercised through the API (IRD-004).

**Users and use cases**
- **Author** — register/login, create/edit draft posts, create categories, assign categories to posts, publish/unpublish posts.
- **Reader** — register/login (required to comment), browse/filter published posts by category, read a single published post, leave/edit/delete their own comments.
- **Admin** — internal moderation persona with elevated platform oversight: can moderate/archive any policy-violating post, delete any comment, and update any user's role. The first Admin account is seeded automatically at user-service startup from `INITIAL_ADMIN_EMAIL` / `INITIAL_ADMIN_PASSWORD` if no users exist yet (see IRD-001).

**Services and ownership**
- **gateway** (PIC: shared) — single entry point; routes requests; validates JWT on protected routes; forwards authenticated user ID and role downstream via `X-User-Id` and `X-User-Role`. Owns no data.
- **user-service** (PIC: Dat Pham) — owns user accounts, registration, login, role management (including admin role updates), and JWT issuance.
- **content-service** (PIC: Trung) — owns posts, categories, and comments.
- **frontend** (PIC: shared) — React SPA (Vite), the only client-facing UI. Calls `gateway` from the browser; owns no data of its own, no server-side logic. Satisfies the Day 9 project-floor requirement ("frontend + backend + database").
- **PostgreSQL** (Storage, not a service) — persistent storage; logical schema separation: `user_db` (user-service), `content_db` (content-service), both created by `postgres-initdb` (`k8s/postgres-initdb-configmap.yaml`, mirrors `infra/init-db.sql`).

**Tech stack** *(added Day 21)*
- Node.js 20 (Express), Knex migrations, bcrypt, JWT HS256; React + Vite; PostgreSQL 16.
- Multi-stage, non-root Docker images on `node:20-alpine` (DOP-002, IRD-006).
- Kubernetes + ingress-nginx (DOP-003, IRD-007); AWS EKS for cloud runs (DOP-004).

**Deployment target** *(added Day 21)*
- Day 9–12: Docker Compose (`docker-compose.yml`) — kept for local dev only.
- **Current reference deployment:** Kubernetes manifests in `k8s/base/` (this repo, namespace `blogcms`), local cluster (minikube / Docker Desktop), Ingress hosts `blogcms.local` (frontend) and `api.blogcms.local` (gateway). See `memory/kubernetes-project.md`.
- Cloud: run once end-to-end on EKS `blogcms-trung-lab` (eu-west-2, Day 17) from a separate manifest set in Trung's repo, then torn down. That set was merged into `k8s/overlays/eks/` and deleted on 2026-10-17 — **one manifest set** (DOP-003 AC-1).
- Next: CI/CD (Days 23–26) builds and deploys on commit.

**How the agent uses this DOP**
When implementing any task tied to this DOP, the agent must:
1. Read this DOP to understand the overall goal, service ownership, scope and out-of-scope list
2. Read the linked IRD (IRD-001/002/003/004 per service; IRD-006/007/008 for cross-cutting conventions)
3. Verify each implementation decision against the Scope and Acceptance Criteria above
4. Never let a service accept a client-supplied `role` on public registration, and never let `GET /posts/:id` leak non-published content — these are settled security rules, not open decisions
