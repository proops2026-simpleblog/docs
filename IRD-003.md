# IRD-003 — Gateway & Infrastructure

**Routing table**

| Path Pattern | Target Service | Auth Required | Allowed Roles |
|---|---|---|---|
| `POST /auth/register`, `POST /auth/login` | user-service | No | Any |
| `GET /posts`, `GET /posts/:id`, `GET /categories` | content-service | No | Any (content-service itself enforces per-post visibility — see IRD-002) |
| `POST /posts`, `PATCH /posts/:id` | content-service | Yes | AUTHOR, ADMIN |
| `POST /categories` | content-service | Yes | AUTHOR, ADMIN |
| `POST /posts/:id/comments`, `PATCH /comments/:id`, `DELETE /comments/:id` | content-service | Yes | READER, AUTHOR, ADMIN |
| `GET /health`, `GET /user-service/health`, `GET /content-service/health` | gateway / internal | No | Any |

**JWT middleware logic**
1. Extract `Authorization: Bearer <token>` header from incoming request
2. If route requires auth and header is missing or malformed → return `401 Unauthorized`
3. Verify JWT signature using `JWT_SECRET` and check token expiry
4. On verification success:
   - Extract `sub` (User ID) and `role` (User Role) from token payload
   - Forward request to target service with HTTP headers:
     `X-User-Id: <user_id>`
     `X-User-Role: <user_role>`
5. On public routes (no auth required): forward request directly without JWT verification. If a valid token is present, still forward `X-User-Id` / `X-User-Role` — this lets content-service apply the per-post visibility rule in IRD-002 (e.g. an author viewing their own draft on a nominally "public" route).

**Error payload format (Standardized Across All Services)**
Every error response returned by Gateway or Microservices must follow this exact JSON structure:
```json
{
  "error": "Forbidden",
  "message": "You do not have permission to update this resource",
  "statusCode": 403,
  "timestamp": "2026-08-18T19:50:00.000Z"
}
```

**Trust boundary**
`content-service` and `user-service` must trust the `X-User-Id` and `X-User-Role` headers ONLY on requests arriving from `api-gateway` over the internal Docker network. Microservices must NEVER be exposed directly to the public internet. Only `api-gateway` binds and publishes a public host port.

**Docker Compose spec**
- Services: `api-gateway` (:3000), `content-service` (:3001), `user-service` (:3002), `postgres` (:5432)
- Health check: Each HTTP service exposes `GET /health -> 200 { status: "ok" }`; `postgres` uses `pg_isready -U postgres`
- Service dependency: `api-gateway` depends on `content-service` and `user-service` with `condition: service_healthy`; services depend on `postgres` with `condition: service_healthy`
- Configuration: Environment variables only (`DATABASE_URL`, `JWT_SECRET`, `PORT`) via `.env` file — no hardcoded credentials

**Non-functional requirements**
- Each service runs in its own isolated Docker container
- Standardized `GET /health -> 200` endpoint on every HTTP service
- Standardized error payload structure across all microservices
- Port discipline: Only `api-gateway` maps a port (`3000:3000`) to host; backend microservices are internal-network-only
