# IRD-003 — Gateway & Infrastructure

**PIC:** Shared (Dat Pham & Trung)

**Scope:** Cross-cutting infrastructure that all DOP-001 acceptance criteria depend on.

## Routing Table

| Path Pattern | Target Service | Auth Required | Allowed Roles |
|---|---|---|---|
| `POST /auth/register`, `POST /auth/login` | user-service | No | Any |
| `PATCH /users/:id/role` | user-service | Yes | ADMIN |
| `GET /posts`, `GET /posts/:id`, `GET /categories` | content-service | No | Any (content-service enforces per-post visibility — see IRD-002) |
| `POST /posts`, `PATCH /posts/:id` | content-service | Yes | AUTHOR, ADMIN |
| `POST /categories` | content-service | Yes | AUTHOR, ADMIN |
| `POST /posts/:id/comments`, `PATCH /comments/:id`, `DELETE /comments/:id` | content-service | Yes | READER, AUTHOR, ADMIN |
| `GET /health`, `GET /user-service/health`, `GET /content-service/health` | gateway / internal | No | Any |

**JWT middleware logic**
1. Extract `Authorization: Bearer <token>` header from incoming request
2. If route requires auth and header is missing or malformed → return `401 Unauthorized`
3. Verify JWT signature (`HS256`) using `JWT_SECRET` and check token expiry
4. On verification success: extract `sub` (User ID) and `role` (User Role) from token payload, forward request to target service with headers `X-User-Id` and `X-User-Role`
5. On public routes (no auth required): forward request directly without JWT verification. If a valid token is present, still forward `X-User-Id` / `X-User-Role` — this lets content-service apply the per-post visibility rule in IRD-002.

**Error payload format (standardized across all services)**
```json
{
  "error": "Forbidden",
  "message": "You do not have permission to update this resource",
  "statusCode": 403,
  "timestamp": "2026-08-18T19:50:00.000Z"
}
```

**Trust boundary**
`content-service` and `user-service` must trust the `X-User-Id` and `X-User-Role` headers ONLY on requests arriving from `gateway` over the internal network (Compose network / cluster network). Microservices must NEVER be exposed directly to the public internet. Only `gateway` (and, separately, `frontend` — see below) is reachable from outside; `user-service`, `content-service` and `postgres` never are. In Kubernetes this means: those three Services are `ClusterIP` only, and the Ingress is the single public entry point.

**Kubernetes spec (reference deployment — added Day 21)**
- Manifests: `k8s/base/` in this repo (Day 15, merged 2026-10-17) + `k8s/overlays/eks/`; conventions in IRD-007. Namespace: `blogcms`.
- Ingress `blogcms-ingress` (ingress-nginx), **host-based**:
  - `blogcms.local` → `frontend:5173`
  - `api.blogcms.local` → `gateway:3000` — host-based, not path-based, because gateway routes carry no `/api` prefix.
- Service discovery: ConfigMap `gateway-config` — `USER_SERVICE_URL=http://user-service:3002`, `CONTENT_SERVICE_URL=http://content-service:3001`. Service names intentionally equal the Compose names, so no code changed.
- Secrets (created with `kubectl create secret`, never committed): `gateway-credentials`, `user-service-credentials`, `content-service-credentials`, `postgres-credentials`.
  - **`JWT_SECRET` must hold the same value in `gateway-credentials` and `user-service-credentials`**, otherwise every token user-service issues fails verification at gateway (401). Two copies of one secret is a drift risk — target: one shared `jwt-secret` object referenced by both Deployments.
- Health: `GET /health` backs readiness + liveness probes on every HTTP service.
- Startup order: K8s has no `depends_on`; backends crash-loop until postgres is Ready, readiness keeps them out of rotation. Apply order in `memory/kubernetes-project.md` §4.
- `user_db` / `content_db` are created by ConfigMap `postgres-initdb` (same SQL as `infra/init-db.sql`).

**Docker Compose spec (local dev only)**
- Services: `gateway` (:3000, repo: `github.com/proops2026-simpleblog/gateway`), `content-service` (:3001), `user-service` (:3002), `frontend` (:5173, repo: `github.com/proops2026-simpleblog/frontend` — see IRD-004), `postgres` (:5432)
- Health check: each HTTP service exposes `GET /health -> 200 { status: "ok" }`; `postgres` uses `pg_isready -U postgres`
- Service dependency: `gateway` depends on `content-service` and `user-service` with `condition: service_healthy`; services depend on `postgres` with `condition: service_healthy`
- Configuration: environment variables only (`DATABASE_URL`, `JWT_SECRET`, `INITIAL_ADMIN_EMAIL`, `INITIAL_ADMIN_PASSWORD`, `PORT`) via `.env` file — no hardcoded credentials

**Non-functional requirements**
- Each service runs in its own isolated Docker container
- Standardized `GET /health -> 200` endpoint on every HTTP service
- Standardized error payload structure across all microservices
- Port discipline (updated after IRD-004): `gateway` (:3000) and `frontend` (:5173) are the only two services that map a host port. `frontend` is a static client with no data access of its own, so exposing it does not weaken the trust boundary — `user-service` and `content-service` remain internal-network-only, and `frontend` still reaches them exclusively through `gateway`, never directly.
