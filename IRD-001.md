# IRD-001 — user-service

**PIC:** Dat Pham

**Scope:** Covers DOP-001 ACs 1, 2, 5 (admin role-override), 9. Depends on: none.

**Tech stack:** Node.js (Express) + bcrypt + JWT (HS256)

## API Contract

```text
POST   /auth/register     { email, password }         -> 201 { id, email, role }
                                                        -> 400 invalid email format
                                                        -> 409 email already exists

POST   /auth/login        { email, password }         -> 200 { token, expiresIn, user: { id, email, role } }
                                                        -> 401 invalid credentials

PATCH  /users/:id/role    { role }        [ADMIN only] -> 200 { id, email, role }
                                                        -> 400 invalid role value
                                                        -> 401 no/invalid token
                                                        -> 403 requester is not ADMIN
                                                        -> 404 target user not found

GET    /health                                         -> 200 { status: "ok", service: "user-service" }
```

## Data Model (`user_db`)

```sql
CREATE TABLE users (
  id            UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  email         VARCHAR(255) NOT NULL,
  password_hash VARCHAR(255) NOT NULL,
  role          VARCHAR(20)  NOT NULL DEFAULT 'READER'
                CHECK (role IN ('READER', 'AUTHOR', 'ADMIN')),
  created_at    TIMESTAMPTZ  NOT NULL DEFAULT now(),
  updated_at    TIMESTAMPTZ  NOT NULL DEFAULT now(),
  CONSTRAINT uq_users_email UNIQUE (email)
);

CREATE UNIQUE INDEX uq_users_email_lower ON users (LOWER(email));
```

## Validation Rules

- Email must be valid email format and globally unique (case-insensitive — enforced via `uq_users_email_lower`)
- Password: required field, minimum 6 characters; hashed with bcrypt, cost factor 10
- **Security rule — role assignment:** `POST /auth/register` does NOT read a `role` field from the request body at all. The server always inserts `role = READER` on self-registration. `AUTHOR`/`ADMIN` roles can only be granted afterward via `PATCH /users/:id/role`, which is restricted to an existing `ADMIN`.
- **Security rule — admin bootstrap:** on startup, user-service checks `SELECT COUNT(*) FROM users`; if zero, it inserts exactly one row with `email = INITIAL_ADMIN_EMAIL`, `password_hash = bcrypt(INITIAL_ADMIN_PASSWORD)`, `role = 'ADMIN'` — bypassing the register-forces-READER rule as the one documented exception. The check makes this idempotent: it only runs when the table is empty, so it is safe to run on every startup.
- JWT: algorithm `HS256`; 24h expiry; payload `{ sub: id, email, role }`; secret from `JWT_SECRET` env var (never hardcoded)

## Test Requirements

- Register: success (201, role always `READER`) + invalid email format (400) + duplicate email (409)
- Register: request body includes `role: "ADMIN"` -> response role is still `READER` (privilege-escalation regression test)
- Login: success (200 with JWT) + wrong password / non-existent user (401)
- Role update: success by ADMIN (200) + non-ADMIN caller (403) + invalid role value (400) + unknown target user (404)
- Startup: empty `users` table seeds exactly one ADMIN row from env vars; re-running startup with existing users does not reseed (idempotency check)
- Health check: returns status "ok" (200)

Precondition: `user_db` exists before first start (`postgres-initdb` ConfigMap).

**Known gap (Day 15):** with `replicas: 2` on an empty `users` table, both Pods run the bootstrap check-then-insert at once; one Pod errors once and recovers on restart. The bootstrap is idempotent per Pod but not race-safe across Pods. Fix: rely on `uq_users_email` and treat a unique-violation during seeding as "already seeded" — tracked as DOP-003 AC-8.
