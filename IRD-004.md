# IRD-004 — frontend

**PIC:** Shared (Dat Pham & Trung)

**Scope:** Client-facing UI for all DOP-001 acceptance criteria. Depends on: `gateway` only — never calls `user-service` or `content-service` directly, and never touches the database.

**Tech stack:** React (Vite). No server-side rendering, no backend logic of its own.

## API base URL

The frontend runs in the **browser on the host machine** — it is never a member of the Compose network `blogcms-net`, so it cannot use service-name DNS (`http://gateway:3000`) the way containers do. It must call the gateway's **published host port** instead:

```
VITE_API_BASE_URL=http://localhost:3000
```

This is the same distinction Q4 established: DNS-by-service-name only works container-to-container. A browser tab, even one opened on the same machine running Docker, is outside that network and must go through the mapped host port like any other external client — exactly like Postman or `curl` would.

**Kubernetes (Day 15, updated Day 21):** the same rule applies — the browser is outside the cluster and can never use a Service DNS name. The value comes from ConfigMap `frontend-config`:

| Environment | `VITE_API_BASE_URL` |
|---|---|
| Docker Compose (local dev) | `http://localhost:3000` |
| Kubernetes (`k8s/base/`, local cluster) | `http://api.blogcms.local` (Ingress host → `gateway:3000`) |

The Vite dev server must allow the Ingress host: `server.allowedHosts: ['blogcms.local']` in `vite.config.js` (`frontend@a1b23dd`), otherwise Vite answers `Blocked request. This host is not allowed`.

## Auth / token handling (security rule)

- On successful `POST /auth/login`, the JWT is kept **in memory only** (React state / a request-scoped auth context) — **never in `localStorage` or `sessionStorage`.** Storing a JWT in browser storage makes it readable by any injected script (XSS), and this app has user-generated content (post bodies, comments) rendered back to other users — exactly the kind of surface where an XSS-stored token becomes a real account-takeover risk, not a theoretical one.
- Every authenticated request attaches `Authorization: Bearer <token>` from that in-memory value.
- Trade-off, stated explicitly rather than hidden: a page refresh loses the session and requires re-login. Accepted for Sprint scope — a refresh-token / httpOnly-cookie flow is a legitimate future improvement, not required now.

## Pages / routes (minimum for DOP-001's 9 ACs)

| Route | Purpose | Auth |
|---|---|---|
| `/register`, `/login` | AC1, AC2 | Public |
| `/` (post list, category filter) | AC6 | Public |
| `/posts/:id` (read post + comments) | AC7, AC8 | Public (extra fields shown if owner/admin) |
| `/posts/new`, `/posts/:id/edit` | AC3, AC4, AC5 | AUTHOR/ADMIN only |
| `/categories` (create) | AC4 | AUTHOR/ADMIN only |

Role-based admin tooling (role updates, moderation) is **out of scope for this IRD's first pass** — Admin actions from DOP-001 can be exercised directly against the API (Postman/curl) for Sprint 1; a dedicated admin UI is a later addition, not a gap in this IRD.

## Validation rules

- Client-side form validation (required fields, email format) is a UX convenience only — it must never be treated as the security boundary. Every rule already enforced server-side (forced `READER` role, ownership checks, draft visibility) stays enforced server-side regardless of what the UI does or doesn't check.
- All error responses from `gateway` follow the standardized payload from IRD-003 (`error`, `message`, `statusCode`, `timestamp`) — the frontend renders `message` directly, it does not need its own error-code mapping table.

## Non-functional requirements

- Runs in its own Docker container (Vite dev server for Sprint 1 simplicity); a production multi-stage build served via Nginx is a documented future improvement, not required now.
- Configuration via environment variable only (`VITE_API_BASE_URL`) — no hardcoded API URL.
- No `.env` secrets needed — the frontend holds no credentials of its own (it only ever forwards the user's own JWT, obtained via login).
