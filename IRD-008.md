# IRD-008 — Helm Chart Conventions

**PIC:** Trung
**Implements:** DOP-003 Orchestration
**Status:** ACTIVE (no release in scope yet) · **Last updated:** 2026-10-17 (Day 21)

## 1. Context
The project's only Helm release was `bitnami/redis` (Day 16, adjusted for EKS on Day 17). No service used it, and its values file committed a password with no pinned chart version, so on 2026-10-17 Trung + Dat decided to **remove it** (DOP-001 / DOP-003 Out of scope). The project currently has **no Helm release**. The next third-party charts arrive soon (ingress-nginx on EKS, kube-prometheus-stack in Week 7), so the install / upgrade / rollback pattern is fixed now and applies to the first of those.

## 2. Inputs
- Chart reference with a **pinned chart version**.
- One committed values file per release, `k8s/helm/<release>-values.yaml`, holding only keys that differ from chart defaults, each with a WHY comment.
- Optional environment layer `k8s/helm/<release>-values.<env>.yaml` (e.g. `.eks.yaml`) applied with a second `-f`.

## 3. Outputs
- Helm release in the namespace that owns it (`blogcms` for app dependencies; the chart's own namespace for cluster add-ons such as `ingress-nginx`, `monitoring`) with revision history available for rollback.

## 4. Conventions

| Rule | Required |
|---|---|
| Install / upgrade | `helm upgrade --install <release> <chart> --version <x.y.z> -n <ns> -f <release>-values.yaml [-f <release>-values.<env>.yaml]` — idempotent, same command every time |
| Values | Committed file(s) only; `--set` only for one-off debugging, never for a real deploy |
| Secrets | No password in a values file — use the chart's `existingSecret` pointing at a Secret created per IRD-007 |
| Resources | Set `resources` explicitly for every component (charts warn `resourcesPreset` is not for production) |
| Persistence | `storageClass` set per environment (local `standard`, EKS `gp2-csi`) |
| Review | `helm template … \| diff` (or `helm diff upgrade`) reviewed before every upgrade |
| Rollback | `helm history <release> -n <ns>` → `helm rollback <release> <rev> -n <ns>` |
| Removal | A release nobody uses is uninstalled, not left running — `helm uninstall <release> -n <ns>` after `helm get manifest` review; PVCs from StatefulSets are listed and deleted explicitly |

## 5. Acceptance criteria
- AC-1: `helm get values <release> -n <ns>` equals the committed values file(s).
- AC-2: Chart version is pinned in the install command and recorded in this repo.
- AC-3: No plaintext password in any committed values file.
- AC-4: Re-running the install command produces a new revision with no resource changes.
- AC-5: Rolling back to the previous revision returns the Pod to Ready.
- AC-6: No Helm release exists that no DOP AC requires.

## 6. Dependencies
Helm 3 · chart repo per release · StorageClass per DOP-004 · IRD-007 (namespace, secret policy)

## 7. Tests
```bash
helm list -A                                                       # every release listed has a DOP reason   (AC-6); shows chart version (AC-2)
helm get values <release> -n <ns> -o yaml | diff - k8s/helm/<release>-values.yaml   # no diff            (AC-1)
grep -rn 'password:' k8s/helm/                                     # no output                            (AC-3)
helm upgrade --install <release> <chart> --version <x.y.z> -n <ns> -f k8s/helm/<release>-values.yaml
helm history <release> -n <ns>                                     # new revision                         (AC-4)
helm rollback <release> <prev> -n <ns> && kubectl rollout status <workload> -n <ns>                      (AC-5)
```
Result 2026-10-17: no Helm release in the project — AC-1..5 not applicable until the next chart; AC-6 ✅ on the current cluster (Docker Desktop has no Helm releases; EKS `blogcms-trung-lab` torn down Day 17). The old minikube profile is stopped, not deleted — if it is ever started again: `helm list -n blogcms`, then `helm uninstall my-redis -n blogcms` and delete its `redis-data-*` PVC. `proops2026/k8s/blogcms/my-redis-values.yaml` deleted with Trung's manifest set.
